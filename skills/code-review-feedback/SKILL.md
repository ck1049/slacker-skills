# 代码质量反馈闭环

## 先确定范围和宿主约定

读取仓库工作规则、相关需求、构建入口、格式配置和实际 CI；没有某文件或工具时查找等价物，不依赖固定目录、操作系统或其他 Skill。明确本次是只审查还是审查并修复。固定 base/head 或记录工作区、暂存区及未跟踪文件清单；识别原有改动，不提交、丢弃或隐藏他人的工作。

采用用户明确要求及项目约定；区分语言正确性、项目强制规则、一般建议和个人偏好。既有排版、框架、注释语言、提交语言、目录名不是通用缺陷。不借审查推行统一框架或全仓重排。

## 审查完整调用链

- 阅读本次自有代码变化及必要上下文，跟踪输入、校验、状态变更、副作用和失败回执。生成文件检查生成源及再生一致性，不手修输出。
- 可维护性：职责是否明确、规则是否重复、类型能否表达契约、异常是否失去原因、注释是否解释约束、格式化后链式调用是否仍易读。只建议解决当前问题的抽象。
- 行为：边界输入、权限归属、事务/并发、生命周期、超时后的不确定结果、重试是否产生重复副作用。测试成功不等于这些边界正确。
- 测试：断言是否能在错误实现下失败；关键依赖的 Mock 是否掩盖事务、数据库方言或浏览器真实行为。按风险补行为证据，不追求统一覆盖率数字。
- 性能：用实际输入规模和测量说明退化；没有测量时标待验证，不能以猜测为由重写架构。

## 核实与修复

每项发现记录「位置、触发条件、后果、证据、最小改法、验证方式」。区分已复现、由代码可论证、待核实和维护建议；不输出原始秘密。

只审查时给出可执行反馈；已授权修复时执行发现 → 核实 → 范围内修改 → 相关复测 → 最新差异复查。允许并适合独立审查时使用独立审查者，否则明确自审限制，不伪称独立通过。不要把无关大重构混入修复。争议用契约、代码和实验解决，不依赖模型投票。

运行项目现有格式检查、静态规则、构建和针对风险的测试。新增规则先验证正反样例，例如参数注解同行应通过、成员注解是否独行由项目规则决定；避免一个正则同时匹配完全不同的语法位置。语法规则优先使用语言解析器。缺少检查器时说明缺口并选择兼容方案，不静默全局安装工具或降低规则。

审查暂存变更时，测试也应对应索引快照；未暂存修复不能让索引中的缺陷变为已解决。若只能测试工作区，明确证据所对应的版本和缺口。若修改钩子，检查真实暂存快照而非只检查工作区；不替用户自动暂存修复。CI 文件存在、本地通过、远端执行和合并保护生效是四种不同证据。沿用项目阻断策略；确认的严重行为缺陷与关键测试失败必须明确报告，不能用平均分淡化。纯偏好不自动升级为阻断。

## 收敛与交付

本次验收通过、阻断问题解决、其余发现有修复或延期理由后结束。实质变更后重新确认受影响结论，不继承旧版本批准。报告范围、关键改善、实际命令/结果、未运行项和剩余风险；不能保证绝对正确。提交、推送、合并和发布只沿用用户已有授权，不由本 Skill 自动授予。

## 依据

- [Google 代码审查要点](https://google.github.io/eng-practices/review/reviewer/looking-for.html)：设计、复杂度、测试与上下文审查；不复制其语言偏好为所有团队规则。
- [Git 钩子文档](https://git-scm.com/docs/githooks)：接入时核对所用 Git 的钩子行为，尤其工作目录和失败退出码。

这些链接是规范入口，不锁定项目版本；实施前核对宿主使用的版本及可运行命令。
