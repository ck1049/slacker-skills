# 游戏运行时代码质量

## 识别项目后再修改

读取工作规则、引擎项目清单与版本、语言配置、目标平台、构建脚本和相关场景。识别编辑器代码、运行时代码、生成文件、第三方插件与资源元数据边界。采用项目已有命名、目录、注释语言及格式；不要搬入 Web 后端的 Controller/Service 模板，不强制 ECS、对象池或某一引擎。

只处理授权功能。若引擎、目标平台或性能验收目标无法从仓库确定，提出影响实现的最少问题；工具或目标设备不可用时继续可独立验证的部分，并明确运行验证缺口。安装技能不等于安装或授权启动任何引擎。

## 实现约束

- 分开玩法状态、输入、表现和持久化职责，使一次交互的状态变化可追踪；简单对象不必拆成多层接口。避免多个组件各自维护同一权威状态。
- 明确创建、激活、停用、销毁和场景切换的资源所有权。事件订阅、计时器、协程、异步加载应在匹配生命周期结束或失效；完成回调不得修改已销毁或已复用对象。
- 对象池回收时重置状态和订阅；不把旧请求的回执交给新一轮对象。池化本身不是必需优化，先证明分配压力。
- 区分帧更新、物理步进和暂停时钟；不要把每帧位移量硬编码成固定帧率。需要确定性时确认随机种子、时间来源和执行顺序；固定步长不自动保证跨平台确定性。
- 资源重命名与移动使用引擎支持方式并保留引用元数据。不要直接批量重写场景、资源标识或生成缓存。检查序列化字段更名对已有场景和存档的影响。
- 存档使用明确结构和版本策略，验证缺字段、损坏、写入中断和旧版本读取；生产存档不可用测试清空代替迁移。路径由平台或调用参数提供。
- 联机场景确认服务端与客户端权威边界、重复消息和断线恢复；不要假定本地 UI 验证就是服务端校验。未涉及联网时不引入网络架构。
- 注释解释单位、状态转换和引擎约束，作者、时间和语言沿用项目要求，不批量插入无意义注释。

## 验证与反馈

先运行项目语言格式、静态分析和编译，再运行适合该引擎的逻辑与运行时测试。至少针对实际变更验证一次进入、离开、重入及异常路径；涉及存档和异步对象时覆盖旧状态恢复与晚到回执。

性能问题保留优化前后同场景、同设备、同构建配置的测量，区分 CPU/GPU、内存分配和加载耗时。编辑器流畅、编译通过和目标设备验收分别报告；没有真实构建或设备测量不写“移动端已优化”。禁止用无测量的缓存、池化或并行化增加维护成本。

抽查格式化后可读性、重复玩法规则和生命周期清理；发现问题后核实、做范围内最小修复、复测。报告实际引擎/版本/平台、命令、场景和未测边界；不提交生成缓存或玩家私有存档，不自动发布商店构建。

## 按引擎查阅一手资料

只读取宿主对应的引擎与版本，无需安装其他技能：

- [Unity Profiler](https://docs.unity3d.com/6000.0/Documentation/Manual/profiler-introduction.html)：此链接为 Unity 6.0 示例入口；切换到项目版本后确认测量与设备连接方式。
- [Godot 最佳实践](https://docs.godotengine.org/en/stable/tutorials/best_practices/index.html)：按项目版本核对节点职责、场景组织和脚本约定。
- 其他引擎或自研引擎采用其官方版本文档及仓库现有生命周期契约；没有核实前不套用 Unity/Godot API。
