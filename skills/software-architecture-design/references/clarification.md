# 澄清与决策记录

## 根据未知项选择问题

第一轮从以下维度选最重要的 1—3 项，不逐项审问：

- 谁在什么场景使用？单人、团队、多租户对身份与隔离有何不同？
- 首版必须完成哪条用户流程？明确暂不做的能力和已有替代方案。
- 部署在本机、服务器还是托管平台？已有团队语言、预算、时限和数据约束是什么？

第二轮依据回答追问真正改变架构的边界，例如：

- 操作失败、网络中断或刷新后，应恢复到哪里？能否安全重试？
- 谁能读、改、删和导出数据？外部凭据归谁？是否发生真实收费？
- 验收如何观察？把“快”拆成明确负载/硬件下的延迟和并发目标，把“好看”拆成页面、布局与交互验收。

选项示例：“首版部署在哪里？这会影响数据存储与运维。A 本机单用户；B 一台服务器供团队访问；C 托管平台。可自定义。”不要隐藏成本、把多个独立决定塞进一个选项，或用“推荐”替用户确认。

## 简短记录格式

- 需求标识、背景与核心行为。
- 各轮问题、用户原意和选项/自定义答案。
- 已确认、建议、待核验；没有回答的假设不能标已确认。
- 范围内/外、关键输入输出、数据/权限/成本边界。
- 正常、失败、恢复的验收例子；尚未量化的指标及确认时机。
- 影响的模块和依赖、实施授权、后续变化及被替代决定。

用户改变技术语言或边界时，同步技术选型、架构、计划与入口说明，旧研究注明历史，不保留两套互相矛盾的“当前方案”。续接项目从记录继续，常规修复与实现细节不重复开展两轮问答。
