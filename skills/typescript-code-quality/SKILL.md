# TypeScript 代码质量

先识别宿主项目，再改善当前任务的代码。这里的默认建议不能覆盖用户选择或已有明确规范；发现冲突时说明差异，避免借一次修复统一整个仓库。

## 识别宿主

检查当前目录及上层工作规则、包清单与锁文件、工作区边界、实际运行时、tsconfig 继承链、lint/formatter 配置、CI 和邻近实现。区分浏览器、服务端、库、测试及生成代码；不要仅因存在 TypeScript 就假定使用 Node.js 或 React。

按仓库脚本和锁定工具运行检查，沿用包管理器。只读取与任务相关的配置，不输出环境密钥。已有格式化器是排版依据；没有时先提出最小、兼容的方案，避免安装互相冲突的格式工具。接入新工具前核对其与当前 TypeScript、运行时及 ESLint 版本兼容性。

## 写代码时落实

- 有确定字段的请求、响应和状态使用明确类型；动态键集合才使用索引签名或 `Record`。不要用 `Record<string, unknown>` 隐藏已知契约，也不要给每个局部变量增加无意义类型标注。
- 网络、文件、存储和消息输入需要运行时验证。`as`、泛型请求函数与自动生成接口都不能证明外部数据有效；边界处以 `unknown` 接收并收窄，复用已有验证方式。
- 用可辨识联合表达互斥状态，显式处理空值和缺失字段。避免 `any`、双重断言、非空断言绕过实际风险；必须使用时限定范围并解释依据。
- 异步操作明确等待者、错误归属和清理责任。后台任务必须显式处理失败；`void promise` 不是错误处理。清理真实操作应在其完成或取消后的 `finally` 中发生，不能把组件消失或调用者返回等同于操作完成。
- 对并发请求、超时和重试区分读取与有副作用的写入。一次网络失败不证明服务端未执行；付费或不可重复写操作遵守现有幂等/查询恢复契约，不自行添加隐式重试。
- 模块按变化原因和运行边界拆分；共享类型不能把数据库、密钥或进程依赖带入浏览器。避免为了单个调用创建空洞抽象，也避免让一个模块同时处理协议、业务和视图。
- 没有更明确宿主约定时，`if`、`else`、`for`、`while`、`do` 等流程体使用花括号；表达式箭头函数不因此强制改为块体。用 lint 落实，不靠人工记忆。
- 行长、换行、导入排序遵循宿主配置；将过深链式调用拆为有意义的局部步骤，避免用大量空行掩盖职责混乱。注释解释约束与取舍，不强制特定语言、作者名或时间戳。

## 检查与交付

运行仓库对应的类型检查、lint、格式检查和受影响行为测试；构建工具能输出 JavaScript 不等于完成类型检查。处理当前改动引入的问题，不通过全局关闭规则、降低类型严格性或删除测试使门禁通过。旧项目提升严格性应分范围推进。

新增测试优先覆盖边界数据、拒绝路径、并发顺序及失败后状态，而非重复实现细节。说明改动范围、实际执行结果和未验证限制；如果没有配置某项检查，明确记录，不能把建议写成已通过。

## 官方参考

需要解释类型收窄或配置行为时阅读 [TypeScript 类型收窄](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)；需要配置流程花括号时阅读 [ESLint curly](https://eslint.org/docs/latest/rules/curly)。这两项资料已于 2026-09-19 核对；采用具体版本配置时再核对宿主版本文档，不将文档示例当成项目配置。
